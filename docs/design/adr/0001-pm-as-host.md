# ADR 0001：PM 只做宿主，不做重写

- 状态：已接受
- 日期：2026-11-16
- 影响范围：全部模块

## 背景

目标是让 Nukkit 服务端能加载 PocketMine 的 `.phar` 插件。横在中间的是三层障碍：
PHP 8.1 的运行时语义、数千个 `pocketmine\*` 类的行为、以及 phar/Composer/Virion 的打包生态。

评估过三条路线，其中一条是"用 Java 实现同名 `pocketmine\*` 类，把插件源码
机械转译后编译运行"。这条路看起来最可控，实际上是最贵的。

## 决策

**PocketMine 本体（fork 后）作为插件宿主独立运行，通过 Unix socket 与 JVM 通信。
本项目不实现任何 `pocketmine\*` 的同名类。**

需要 PM 的行为时，改 fork；不需要的，就让插件自己失败。绝不在这里补一份。

## 理由

1. **语义无法复刻。** PM 的类行为是十几年演化的结果，包括大量看起来像 bug 的边界条件。
   重写等于重新发现这些边界，而插件作者早就依赖它们了。
2. **漂移不可测。** 手写的垫片和真 PM 之间没有差分测试可比，因为"正确"的定义就在真 PM 里。
3. **上游已冻结。** PM 于 2026-07-09 归档，基线 5.44.4 不再变动。fork 一次不用追，
   这是整件事可行的时间窗口；重写则要一直追一个不动的目标，纯亏。
4. **假会话可行。** `NetworkSession` 与 `Player` 都不是 `final`，`Player` 构造不发包，
   `NetworkSession::sendDataPacket()` 是 public。这三条让"不重写也能驱动真 PM"成立。
5. **崩溃域隔离。** 独立进程意味着 PHP 挂了不会带走服务端，重写就没有这层缓冲。

## 后果

正面：

- 插件看到的 API 与在 PM 上完全一致（因为就是同一份代码）
- 工程量集中在桥（tick、op、事件），而不是 API 面
- 可以拿"能不能通过 L3"作为唯一的正确性判据

负面：

- 必须维护一个 PM fork，包括五处切口和运行时依赖瘦身
- 宿主进程多一份内存占用
- 跨进程调试成本高于单进程
- LGPL-3.0 的修改需要开源（独立进程不构成链接，边界是干净的）

## 被否方案

| 方案 | 否决原因 |
|---|---|
| JVM 内跑 PHP 解释器（JPHP / Quercus） | 只到 PHP 7.x，`match` / `enum` / `readonly` / 构造器提升全都过不去 |
| php-wasm + JVM 侧 WASM 运行时 | php-wasm 是单线程 CLI 构建，PM 依赖真线程与共享内存；且每次 host call 都要穿越边界 |
| Java 重写 `pocketmine\*` + 源码转译 | 本 ADR 的主要否决对象，见"理由" |
| 让 PM 当主服务端、Nukkit 当代理 | 世界模拟会落到 PM 侧，Nukkit 的生成/红石/AI 全废，与本项目目标相反 |

## 检测漂移

三条机检由 `scripts/check-architecture.sh` 固定；三条人工判断写在
`docs/project/spec/principles.md` 的"第一原则"。

关键的一条：**评审时问"PM 里已经有这个实现了吗"**。有，就是不能写。

## 什么时候重新审视

只有两种情况：

1. PM fork 在纯 PHP 环境下无法 boot（L3 过不了），且原因无法通过改 fork 解决
2. 出现一个能完整承载 PHP 8.1 语义、又能在 JVM 内安全隔离的运行时

两者都没发生之前，本条决策不变。
