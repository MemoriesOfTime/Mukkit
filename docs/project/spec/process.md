# 流程规范

## 分支

- `main` 只接受 PR，不直接推
- 功能分支用 `feature/<slug>`，修复用 `fix/<slug>`
- 实验性 fork 改动放 `fork/<slug>`，不合进主线前必须能通过 L3

## 提交

```
<scope>: <祈使句描述>

可选正文：为什么这么改，代价是什么。
```

`scope` 取模块名：`bridge`、`nukkit`、`spike`、`host`、`fork`、`docs`、`spec`。

例：

```
bridge: 硬超时后不再等待迟到的 tickdone

迟到的帧会污染下一轮的 seq 匹配，直接丢弃并计数更安全。
```

不写"修复了一些问题""优化代码"这种没有信息量的信息。

## 版本与协议演进

- `0.x`：协议可以破，破的时候两侧同一个 PR 改，并 bump `Protocol.VERSION`
- `1.0` 起：`proto` 变更视为不兼容，主版本号 +1
- 新增 op / 新增帧 = 兼容变更，不 bump 版本；对端必须能跳过未知类型
- PM fork 的基线版本写进 `docs/design/pm-fork.md`，升级基线是一次单独的 PR

## 协议变更流程

按顺序做完，缺一步打回：

1. 改 `cn.mukkit.bridge.Protocol` 与 `Mukkit\Host\Protocol`（同一个 PR）
2. 改 `docs/design/protocol.md` 的消息表或 op 表
3. 跑 L1 + L2，贴出 `round trip` 与退出码
4. 如果新增了 op，在 `StubProfile` 里产出一次，证明端到端通

## 文档规范

- 正文中文，代码、标识符、协议字段英文
- 不写版本迁移叙事（"以前是 A，现在改成 B"），当前状态写清楚就够
- 每份文档开头一句说清这份文档解决什么问题
- 流程图优先用文字时序块，不引入绘图依赖
- 新增文档要登记进 `docs/README.md` 的索引

## 评审清单

PR 描述里逐条勾，没勾的不用看：

- [ ] 没有新增 `pocketmine\*` 的本地实现（红线 1、2）
- [ ] 没有反向依赖（`bridge` 不认识 Nukkit，`nukkit` 不认识 PM）
- [ ] 跨进程只走协议，没有共享内存 / JNI
- [ ] 新字段对未知值容错，不会 NPE 到 tick 线程
- [ ] op 和日志带 tick 号
- [ ] 降级有日志，没有静默失败
- [ ] 按"回归要求"跑过对应层级的验证
- [ ] PR 里写明验到哪一层（L0–L5）；真机没做就按"未验债"登记，不许写成"可用"
- [ ] 协议变了就改了 `docs/design/protocol.md`
- [ ] 加模块/加依赖带了 ADR
- [ ] `scripts/check-architecture.sh` 通过

## 什么算"完成"

能跑 ≠ 完成。完成需要：代码 + 验证证据（数字或截图）+ 文档同步。
只有代码的 PR 视为进行中。

"验证证据"要写清层级。L3 全绿而 L4 没跑，正确的说法是"桥内通过，真机未验"；
写成"表单可用"就是虚报，因为没人见过它被画出来。
